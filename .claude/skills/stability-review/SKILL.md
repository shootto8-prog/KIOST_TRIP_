# Stability Review — KIOST 정총무1.0

이 스킬은 "코드가 문법적으로 맞는가"가 아니라 "실제 사용 조건에서 조용히 틀린 결과를 내거나
멈추는가"를 점검하는 방법론이다. 이 앱은 1인 개발자가 무료 티어 인프라 위에서 운영하는 실제
프로덕션 서비스이고, 지금까지 발견된 모든 실버그가 **로컬 개발 환경과 실사용 환경의 차이**에서
나왔다(타임존, 파일 크기, 네트워크 환경, 브라우저 카메라 동작 등). 이 스킬의 체크리스트는 그
패턴을 일반화한 것이다.

## Phase 0: 컨텍스트 확인

1. `_workspace/stability-review/` 디렉토리가 있는지 확인한다.
   - 없으면 **초기 리뷰**: 아래 체크리스트 전체를 훑는다.
   - 있고 사용자가 "다시/재검토/업데이트"라고 했으면 **재검토**: 가장 최근 리포트를 읽고, 이전에
     "높음" 등급이었던 항목이 해결됐는지 먼저 확인한 뒤, 그 사이 변경된 파일(`git diff` 또는
     `git log --since`로 확인) 위주로 훑는다.
   - 사용자가 특정 기능/파일을 지목했으면 **부분 리뷰**: 해당 범위만, 단 관련 있는 다른 파일(예:
     `verifyReceipt.ts`를 보면 반드시 `rules/domestic_travel_rules.json`도 같이)도 함께 본다.
2. `stability-reviewer` 에이전트(`.claude/agents/stability-reviewer.md`)를 `Agent` 도구로
   호출한다 (`model: "opus"`, `subagent_type`은 general-purpose 계열 — Bash로 테스트 실행이
   필요하므로 Explore는 부적합). 프롬프트에 이 SKILL.md 경로와 에이전트 정의 경로를 반드시
   포함해 먼저 읽게 한다.
3. 리뷰 완료 후 `_workspace/stability-review/{날짜}_report.md`가 저장됐는지 확인하고, 핵심 요약을
   사용자에게 전달한다. 심각도 "높음" 항목이 있으면 사용자에게 지금 고칠지 다음으로 미룰지 묻는다
   (코드 수정은 이 스킬의 범위 밖 — 별도 승인 후 진행).

## 점검 카테고리

### 1. 환경 의존성 (로컬 ≠ 프로덕션)

Vercel 서버리스는 UTC로 돈다. 로컬 개발 머신은 KST다. `new Date()`, `.getHours()`,
`.toLocaleString()` 등 **타임존 인자 없이** 호출되는 지점은 전부 의심 대상이다 — 로컬에서는
우연히 맞게 보이고 프로덕션에서만 틀린다(실제로 발견된 버그, `src/lib/kst.ts` 참고). 새로 추가된
날짜/시간 처리 코드가 `kst.ts`의 `parseKstDatetime`/`getKstParts`를 거치지 않고 직접
`new Date()`나 로컬 getter를 쓰면 지적한다.

같은 이유로: 파일 경로 구분자(`\` vs `/`), 폰트/외부 리소스의 절대 경로 하드코딩(과거
`C:\Windows\Fonts\malgun.ttf` 참조가 실제로 있었다), `process.platform` 분기 등도 확인한다.

### 2. 외부 서비스 호출 (OpenRouter, Blob, SMTP, Supabase)

이 앱은 4개의 외부 서비스에 의존하고 전부 무료 티어다. 각 호출부에서:
- **타임아웃/재시도**가 있는가, 없다면 요청이 걸려 사용자가 무한 로딩을 보는 시나리오가
  있는가. (`receiptOcr.ts`는 재시도+폴백 모델이 있음 — 이게 좋은 패턴의 기준선이다. 다른
  외부 호출부가 이 수준에 못 미치면 지적한다.)
- **부분 실패 시 정리(cleanup)가 되는가.** 예: `src/app/api/receipts/route.ts`는 여러 장의
  사진을 순차 처리하는데, N번째 사진에서 실패하면 이미 성공한 1~N-1번째 사진이 만든 부작용(예:
  PDF 페이지를 새 PNG blob으로 재업로드한 것)이 정리되지 않고 Vercel Blob에 고아로 남는다 —
  이런 "일부만 성공한 트랜잭션" 패턴을 찾는다.
- **삭제가 실제로 저장공간을 회수하는가.** DB row만 지우고 Blob의 실제 파일은 안 지우면
  영구적인 저장공간 누수다(무료 티어 용량이 빤한 상황에서 특히 중요). `DELETE` 핸들러들을 훑어
  Blob/파일 삭제가 짝을 이루는지 확인한다.
- **레이트리밋/429 처리.** 무료 LLM 모델은 동시 사용자가 몇 명만 몰려도 429가 난다. 폴백이
  없거나, 폴백까지 실패했을 때 사용자에게 "재시도 가능한 일시적 오류"인지 "이 영수증은 원래
  안 되는 것"인지 구분되는 메시지가 가는지 확인한다.

### 3. 파일 업로드 경로 (모바일 카메라 실사용)

사용자의 실제 사진은 5~10MB+, HEIC/HEIF 포맷, 때로는 여러 페이지 PDF다. 업로드 관련 코드에서:
- 클라이언트→Blob 직접 업로드(`@vercel/blob/client`)와 서버 경유 업로드가 섞여 있지 않은지 —
  섞이면 4.5MB 한도가 예고 없이 재발한다.
- `handleUpload`의 `allowedContentTypes`/`maximumSizeInBytes`가 실제 프론트에서 받는 파일
  종류·크기와 일치하는지.
- PDF 다중 페이지 → 여러 이미지로 펼쳐 OCR에 전부 넘기는 로직(`pdfToImage.ts`,
  `receipts/route.ts`)이 페이지 수가 많을 때(예: 10페이지) 처리 시간/토큰/메모리 한도를 넘길
  가능성.

### 4. OCR/LLM 결과를 신뢰하는 경계

이 앱의 설계 원칙은 "LLM은 텍스트만 추출, 판정은 결정론적 규칙(`verifyReceipt.ts` +
`rules/domestic_travel_rules.json`)"이다. 이 경계가 지켜지는지 확인한다:
- LLM이 반환한 `amount`/`datetime`/`merchant`를 검증 없이 그대로 최종 판정에 쓰는 곳이 있는가.
- 여러 장의 사진을 "같은 문서의 다음 페이지"로 가정하고 한 번의 OCR 호출에 합쳐 보내는 로직
  (조식은 1장 제한으로 이미 막았지만, 숙박(LODGING)은 여전히 다중 페이지를 허용 — 실제로
  사용자가 서로 다른 여러 건의 숙박 영수증을 한 번에 올려 문서 5개가 뒤섞여 병합된 사례가 있었다).
  이런 "여러 개의 서로 다른 거래가 한 OCR 호출에 섞일 수 있는" 지점을 찾고, 완전히 막을 수
  없다면 최소한 감지(예: 서로 다른 사업자등록번호가 N개 이상 나오면 경고)할 수 있는지 짚는다.
- JSON 파싱 실패, 필드 누락, 모델이 형식을 안 지킨 경우의 폴백이 "조용히 통과"가 아니라
  "명시적으로 거부/재확인 요청"인지.

### 5. 동시성/경쟁 상태

Prisma 호출이 순차적인지, 같은 리소스(같은 trip, 같은 receipt)에 대해 동시에 두 요청이 오면
어떻게 되는지(예: 같은 영수증을 두 번 빠르게 재분석 요청). DB 트랜잭션(`prisma.$transaction`)이
필요한데 없는 다단계 쓰기가 있는지(예: receipt 생성 + image 생성이 원자적이지 않으면 이미지 없는
receipt이 남을 수 있는가).

### 6. 사용자 입력 검증 및 데이터 무결성

API 라우트의 입력 검증 수준을 훑는다 — 타입 체크는 있는지, 존재하지 않는 tripId/receiptId로
호출됐을 때 500 대신 명확한 404가 오는지, `owner_email` 쿠키 기반 필터링(`src/lib/identity.ts`)
이 실제 접근 제어가 아니라는 걸 감안했을 때(직접 URL 접근 시 다른 사람 데이터 노출) 이게 정말
문제 없는 설계 전제인지 재확인.

### 7. 배포/설정 드리프트

`package.json`의 `postinstall`(Prisma generate 빠지면 프로덕션 전체가 500 — 실제로 있었던
사고), 환경변수 참조(`process.env.X`)에 대응하는 값이 `.env.example`이나 문서에 다 기록돼
있는지, 새 환경변수가 추가됐는데 "추가 후 재배포 안 하면 반영 안 됨"이라는 이 프로젝트의 반복된
함정에 걸릴 여지가 있는지.

## 출력 형식

`_workspace/stability-review/{YYYY-MM-DD}_report.md`:

```markdown
# Stability Review — {날짜}

## 요약
- 높음 N건 / 중간 N건 / 낮음 N건

## 높음
### {한 줄 요약, 전문용어 없이}
- 파일: `path/to/file.ts:123`
- 실패 시나리오: {구체적 입력} → {구체적으로 틀린 결과 또는 장애}
- 근거: {코드 인용/설명}
- 제안: {선택, 짧게}

## 중간
(동일 형식)

## 낮음
(동일 형식, 간략히)

## 확인 불가 / 의심됨
(근거는 있으나 재현 확인 못한 항목)
```

## 테스트 시나리오

- **정상 흐름**: 사용자가 "안정성 검토해줘"라고 요청 → Phase 0에서 `_workspace/stability-review/`
  없음 확인 → 초기 리뷰로 stability-reviewer 에이전트를 opus로 호출 → 에이전트가 7개 카테고리를
  훑고 리포트 저장 → 메인이 심각도 높음 항목 요약해 보고.
- **에러 흐름**: stability-reviewer가 특정 파일(예: 삭제된 파일)을 못 읽음 → 해당 항목을
  "확인 불가"로 표시하고 나머지 카테고리는 계속 진행 → 최종 리포트에 "확인 불가" 섹션으로 남음
  (리뷰 전체가 중단되지 않음).
