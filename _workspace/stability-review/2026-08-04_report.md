## 높음

### 1. 항공권을 예매일에 결제하면(=거의 모든 경우) 정상 영수증이 "날짜 불일치"로 반려된다
- 파일: `src/lib/verifyReceipt.ts:231`, `src/lib/verifyReceipt.ts:271`, `src/lib/receiptOcr.ts:21-22`
- 실패 시나리오: 8/10~8/12 출장, 항공권을 7/15에 예매·결제 → OCR 프롬프트가 "**결제** 일시"를 뽑으라고 지시 → `ocrDateGuess = 2026-07-15` → `isWithinTripDateRange` 실패 → **REJECTED "영수증 날짜가 출장기간과 일치하지 않습니다"**. 숙박 선결제(예약 시 결제)도 동일.
- 근거: 교통·숙박 모두 공통 `trip_date_mismatch` 검사를 결제일에 적용한다. 조식은 당일 결제라 문제없지만, 항공/선박/숙박은 사전 결제가 정상이다. 실비정산에서 판단해야 할 날짜는 **탑승일/투숙일**이지 결제일이 아니다.
- 제안: 교통·숙박은 결제일 대신 이용일(탑승일/체크인일)을 추출하도록 프롬프트를 나누거나, 최소한 결제일이 출장 전이면 반려 대신 "확인 필요"로 통과시킨다.

### 2. 교통 항목에 교통과 무관한 영수증이 섞여도 금액이 그대로 합산돼 과다 인정된다
- 파일: `src/lib/analyzeReceipt.ts:98-118`, `src/lib/verifyReceipt.ts:207-233`
- 실패 시나리오: 항공권 사진 + 실수로 호텔 영수증 사진을 교통 항목에 함께 등록 → `runOcrSummed`가 성공한 모든 사진 금액을 무조건 더함(107행) → 항공권 45,000 + 호텔 150,000 = **195,000원이 교통비로 APPROVED**.
- 근거: 검사(업체유형/좌석등급/장소)는 사진별이 아니라 이어붙인 전체 텍스트 한 덩어리에 대해 1회만 수행된다. 사진1에 "항공권"이 있으면 사진2가 무엇이든 `not_transport_receipt`를 통과한다.
- 제안: 사진별로 `required_keywords` 검사를 먼저 하고, 통과한 사진의 금액만 합산한다.

### 3. 교통 사진 중 일부만 인식 실패해도 "성공"으로 표시되고 금액이 조용히 빠진다
- 파일: `src/lib/analyzeReceipt.ts:99-117`
- 실패 시나리오: 왕복 항공권 2장 등록 → 2번째가 무료 모델 429/흐림으로 실패 → `succeeded.length === 1` → `ocrStatus: "DONE"`, 합계 = 편도 금액만. 화면엔 "인식 합계금액 45,000원"이 정상처럼 뜨고, `verdictFailedCheck`가 `ocr_unavailable`이 아니라 **"다시 인식 시도" 버튼도 나오지 않는다**. 사용자는 편도 값만 정산받고 끝난다.
- 근거: 107행이 `succeeded`만 더하는데 108-116행이 상태를 무조건 `DONE`으로 승격한다.
- 제안: 실패한 사진이 하나라도 있으면 PARTIAL/경고 메시지 + 재시도 버튼 노출.

### 4. 영수증·출장을 지워도 사진 파일은 Vercel Blob에 영구히 남는다 (무료 용량 잠식)
- 파일: `src/app/api/receipts/route.ts:153-161`, `src/app/api/trips/[id]/route.ts:98-101`
- 실패 시나리오: 사용자가 잘못 찍은 사진을 지우고 다시 올리기를 반복 → DB는 깨끗하지만 Blob 사용량만 단조 증가 → 무료 한도 소진 후 업로드 전면 실패.
- 근거: 코드베이스 전체에 `@vercel/blob`의 `del()` import/호출이 **하나도 없다**(grep 확인). 출장 삭제는 대신 `public/uploads/{id}` **로컬 디렉토리**를 지우려 하는데(100행), 이는 Blob 전환 이전의 잔재라 Vercel에서는 존재하지도 않는 경로이고 `.catch(() => {})`로 조용히 무시된다.
- 추가 누수 경로: 브라우저가 Blob에 먼저 올린 뒤 `POST /api/receipts`가 실패하면(사진 fetch 실패 76행, PDF 변환 실패 92행, 사용자가 창을 닫음) DB에 기록조차 안 된 고아 파일이 남는다. PDF는 첫 페이지 PNG를 **추가로 한 번 더** 올리므로(100-103행) 원본 PDF + PNG 둘 다 고아가 된다.
- 제안: DELETE 핸들러에서 `del(images.map(i => i.path))` 호출, POST 실패 경로에 정리 로직 추가, trip DELETE의 `rm(public/uploads/...)`는 제거.

### 5. 정산서 PDF가 원본 사진을 축소 없이 그대로 넣어, 이메일 발송이 실패하거나 서버가 시간 초과된다
- 파일: `src/lib/generatePdf.ts:73-118`, `:218-219`, `:233-235`
- 실패 시나리오: 3박 출장에 조식3 + 교통2 + 숙박1 + 현장사진5 = 11장, 아이폰 사진 장당 4~6MB → 화면 배치는 220pt로 줄이지만 `embedPng`/`embedJpg`는 **원본 바이트를 그대로** 삽입 → 결과 PDF가 50MB 이상 → Gmail 첨부 한도(25MB) 초과로 이메일 발송 실패(502), 또는 이미지를 한 장씩 순차 `await fetch`(218행)하다가 서버리스 함수 시간 제한 초과로 다운로드 자체가 실패.
- 근거: 112행의 `scale`은 그리기 좌표만 줄이고 삽입 데이터는 줄이지 않는다. 폰트도 `subset: false`로 Regular+Bold 전체를 임베드한다(133-134행, 수 MB).
- 제안: 삽입 전 리사이즈(장당 200~300KB 목표), 또는 PDF엔 축소본만 넣기.

### 6. 외부 호출에 타임아웃이 전혀 없어, 한 번 걸리면 사용자는 무한 로딩 뒤 "네트워크 오류"만 본다
- 파일: `src/lib/receiptOcr.ts:109`, `src/app/api/receipts/route.ts:71`, `src/app/api/receipts/[id]/reanalyze/route.ts:40`, `src/lib/generatePdf.ts:79`
- 실패 시나리오: OpenRouter 무료 모델이 응답을 안 주고 연결만 유지 → `fetch`에 `AbortController`/`signal`이 없어 무한 대기 → 재시도 로직(158-172행)은 **에러가 났을 때만** 도는 구조라 아무 역할도 못 함 → Vercel이 함수를 강제 종료 → 프론트는 `res.json()` 실패 → `ReceiptManager.tsx:280`이 전부 "네트워크 오류가 발생했습니다"로 뭉갠다. 사용자는 재시도해야 할지 이 영수증이 원래 안 되는 건지 구분할 수 없고, 그 사이 Blob 파일은 이미 올라가 고아로 남는다(항목 4).
- 근거: 정상 경로에서도 최악의 경우 1차 2회 + 폴백 2회 = LLM 호출 4번 + `sleep` 5초가 **직렬로** 쌓인다. `maxDuration` export는 코드 전체에 없다(grep 확인) → 플랫폼 기본값에 그대로 노출.
- 제안: 모든 외부 `fetch`에 `AbortSignal.timeout(20000)` 수준의 상한, 라우트에 `export const maxDuration` 명시, 타임아웃은 "일시적 오류, 재시도 가능"으로 구분된 메시지.

## 중간

### 7. 숙박은 서로 다른 여러 건의 영수증을 한 번에 올려도 감지하지 못한다 (조식에만 있는 방어가 빠져 있음)
- 파일: `src/lib/verifyReceipt.ts:256-306`, `rules/domestic_travel_rules.json:198-232`, `src/components/ReceiptManager.tsx:320`
- 근거: 조식에는 `max_receipts: 1` + 서로 다른 사업자등록번호 개수 검사가 있지만(`verifyReceipt.ts:157-161`), 숙박 `checks`에는 `multiple_receipts` 항목 자체가 없다. 오히려 안내문이 "여러 장이면 같은 영수증의 다음 페이지로 보고 합쳐서 인식합니다"라 다중 업로드를 권장한다.
- 실패 시나리오(실제 발생 사례): 서로 다른 숙소 5건을 한 번에 등록 → 프롬프트가 "하나의 최종 금액만 답하라"고 지시하므로(`receiptOcr.ts:24-25`) 모델이 임의로 한 건만 고르거나 전부 더한다 → 어느 쪽이든 사용자도 검토자도 어떤 금액인지 알 수 없다.
- 제안: `verifyReceipt.ts:157`의 사업자등록번호 카운트 로직을 숙박에도 그대로 적용해, 2개 이상이면 "여러 건의 영수증이 섞였습니다"로 반려/경고.

### 8. 숙박 상한이 영수증 1건마다 적용돼, 여러 건으로 나눠 올리면 상한이 무력화된다

- 실패 시나리오: 3박 출장 → 건당 상한 `capForStay = 360,000`. 숙박 영수증을 3건으로 나눠 각 350,000원 등록 → 3건 모두 APPROVED → 숙박 합계 **1,050,000원**(규정 상한 360,000원).
- 제안: 출장 단위 누적 상한 검사, 또는 숙박은 출장당 1건으로 제한.

### 9. 인증 없는 공개 API가 전 사용자의 출장과 이메일을 노출한다 (프로덕션에서 실제 확인함)
- 파일: `src/app/api/trips/route.ts:58-64`
- 근거: `GET https://kiost-trip-delta.vercel.app/api/trips`를 아무 인증 없이 호출하면 출장 4건과 서로 다른 실제 이메일 3개(`youn***@kiost.ac.kr` 등)가 그대로 반환된다. 홈 화면은 서버 컴포넌트에서 Prisma를 직접 쓰므로(`src/app/page.tsx:34-46`) **이 라우트를 호출하는 코드는 앱 어디에도 없다**(grep 확인) — 쓰지도 않는 라우트가 데이터만 흘리고 있다.

- 제안: 미사용 `GET /api/trips` 삭제, 나머지는 최소한 쿠키 `owner_email` 일치 확인.

### 10. PDF로 올린 영수증은 "다시 인식 시도"를 누르면 2페이지 이후 정보가 사라져 판정이 뒤집힌다
- 파일: `src/app/api/receipts/[id]/reanalyze/route.ts:37-47`, `src/app/api/receipts/route.ts:99-104`
- 실패 시나리오: 1p 항공권 요약 + 2p 결제내역 PDF → 최초 등록 시엔 두 페이지 모두 OCR되어 금액 인식, APPROVED. 나중에 재분석하면 저장된 건 1페이지 PNG뿐이라 금액을 못 찾아 **REJECTED로 덮어써지고 원래 값은 복구 불가**.
- 제안: 렌더링한 모든 페이지를 Blob에 저장하거나, PDF 출처 영수증은 재분석 시 경고.

### 11. HEIC 사진은 업로드는 되지만 파이프라인 뒷단이 처리하지 못한다
- 파일: `src/app/api/receipts/upload/route.ts:23-24`, `src/lib/receiptOcr.ts:8`, `src/lib/generatePdf.ts:97-104`
- 근거: `allowedContentTypes`에 `image/heic`·`image/heif`가 있어 업로드는 성공하지만, OCR은 `data:image/heic;base64,...`로 전송해 모델이 디코딩하지 못하고, PDF는 `.heic` 확장자를 "미리보기 미지원"으로 건너뛴다. 결과적으로 판정도 안 되고 정산서에 사진도 안 들어간다. (iOS Safari가 대개 JPEG로 변환해 주므로 항상 재현되진 않음 — 아래 "확인 불가" 참조.)
- 제안: 허용 목록에서 HEIC를 빼서 브라우저가 변환하도록 강제하거나, 서버에서 변환.

### 12. 파일 타입이 비어 있으면 업로드 실패인데 메시지는 "네트워크 오류"

### 13. 업로드 토큰 발급에 아무 검증이 없다
- 파일: `src/app/api/receipts/upload/route.ts:14-28`
- `onBeforeGenerateToken`이 `tripId` 존재 확인도 소유자 확인도 하지 않는다. URL만 알면 누구나 30MB 파일을 이 프로젝트 Blob에 무제한 올릴 수 있어 무료 용량/전송량이 외부에서 소진될 수 있다.

### 14. LLM 구조화 추출이 실패했을 때의 폴백이 카드 승인번호를 금액으로 집을 수 있다

- 제안: 폴백 금액은 판정에 쓰지 말고 "확인 필요"로 처리하거나, 최소한 화면에 "추정값" 표시.

### iOS Safari의 HEIC 자동 변환 여부
- 항목 11의 실제 재현 여부는 iOS Safari가 `<input type="file" accept="image/*">`에서 HEIC를 JPEG로 자동 변환하는지에 달려 있다. 대부분의 iOS 버전에서 변환해 주는 것으로 알려져 있어 항상 재현되지는 않을 것으로 보인다. 다만 코드가 `image/heic`을 명시적으로 허용하고 `.heic` 분기까지 갖고 있다는 건 누군가 이 경로를 예상했다는 뜻이므로, 실제 아이폰에서 갤러리 선택으로 1회 검증할 것을 권한다. (에이전트는 실기기 접근이 없어 미검증.)

## 결정 사항 (2026-08-04 논의)

구현은 아직 하지 않음 — 아래는 각 항목에 대해 사용자와 합의한 조치 내용이다. 다음 세션에서 이 목록대로 구현한다.

### 1. 항공/선박 날짜 검증 제외 — **채택**
`verifyTransport`의 순서4(`isWithinTripDateRange` 체크, `verifyReceipt.ts:230-233`)는 코드 구조상
**이미 AIR/SHIP에만 적용되고 있었다** (RAIL/PRIVATE_CAR/BUS는 정액정산이라 `isFlatRateTransportMode`
분기에서 이 검사 자체를 안 거침). 따라서 이 검사 블록을 통째로 삭제하면 사용자가 제안한 대로
"항공/선박에서 날짜 검증 제외"가 정확히 달성되고, 예매일 선결제로 인한 오반려가 사라진다.
- 조치: `verifyReceipt.ts:230-233`의 `trip_date_mismatch` 체크 블록 삭제.
- 트레이드오프(참고용, 조치 변경 없음): 날짜 검사를 없애면 완전히 무관한 다른 출장의 옛날 항공권
  영수증을 실수로 다시 올려도 막히지 않는다. 다만 업체유형/좌석/장소 검사는 그대로 남아 있고,
  `ocrDateGuess`도 화면에 계속 표시되므로 필요하면 검토자가 육안으로 확인할 수 있다.

### 2. 교통 다중 사진 개별 검증 — **채택**
사진별로 `required_keywords`(업체유형) 검사를 먼저 통과한 사진의 금액만 합산하도록 변경.
검증 실패한 사진은 합계에서 제외하고, 제외됐다는 사실을 사용자에게 표시(항목 3의 부분실패
처리와 같은 방식으로 묶어서 구현).

### 3. 교통 부분 인식 실패 시 상태 표시 — **채택**
사진 중 일부가 OCR 실패하면 `ocrStatus`를 `DONE`으로 승격하지 않고 부분실패로 표시,
"다시 인식 시도" 버튼 노출.

### 4. Blob 삭제 기능 추가 — **채택 (범위 확장: 삭제/제거 기능 명시적으로 추가)**
- 영수증 삭제(`DELETE /api/receipts`)·출장 삭제(`DELETE /api/trips/[id]`) 시 연결된 Blob 파일도
  `@vercel/blob`의 `del()`로 함께 삭제.
- 더 이상 존재하지 않는 로컬 경로(`public/uploads/{id}`)를 지우려는 죽은 코드 제거.
- `POST /api/receipts` 처리 중간에 실패하면(사진 fetch 실패, PDF 변환 실패 등) 그 요청에서 이미
  올라간 Blob 파일들을 정리(삭제)하는 로직 추가.
- (신규) 사용자가 이미 저장된 영수증 사진을 삭제/교체할 수 있는 기능이 없다면, 개별 사진 단위
  삭제 UI도 함께 검토 — 잘못 올라간 사진 하나 때문에 영수증 전체를 지우고 다시 올리지 않아도 되게.

### 5. 정산서 PDF 이미지 리사이즈 — **채택**
> **Q: 새로 사진 찍는 경우도 포함되나?** → 그렇다. 카메라로 찍든 갤러리에서 고르든 결국 같은
> 업로드 경로(브라우저→Blob→`POST /api/receipts`)를 거쳐 같은 방식으로 저장되고, PDF 생성은
> 그 저장된 파일을 나중에 읽어와 조립하는 별개 단계다. 즉 리사이즈를 "PDF를 만드는 시점"에
> 적용하면 사진의 출처(촬영/선택)와 무관하게 전부 적용된다.
- 조치: `generatePdf.ts`에서 이미지를 삽입하기 전에 리사이즈(장당 200~300KB 목표)하거나, PDF
  전용 축소본을 별도로 준비해 삽입한다. OCR/원본 표시용 파일은 그대로 유지(OCR 정확도 유지 목적).

### 6. 외부 호출 타임아웃 — **채택**
모든 외부 `fetch`(OpenRouter, Blob 원본 fetch, PDF 이미지 fetch)에 `AbortSignal.timeout(...)` 상한
추가, 필요한 라우트에 `export const maxDuration` 명시, "네트워크 오류" 메시지를 원인별로 세분화
(타임아웃=재시도 가능 vs 형식 오류=재시도해도 소용없음).

### 7. 숙박 다중 문서 감지 — **채택, 기준 재보완 (2단계 신호 결합)**
**중요 — 적용 범위 오해 주의**: 이 검사는 "출장 전체에서 숙박 영수증을 몇 개 등록하느냐"와 무관
하다. 3박이든 20박이든 숙박 영수증을 원하는 만큼 **따로따로** 등록하는 데는 아무 제한이 없다.
이 검사는 오직 **영수증 한 건(=한 번의 업로드/한 번의 OCR 호출) 안에** 서로 무관한 문서가
섞여 들어갔는지만 본다.

1차 보완안(사업자등록번호 3개 이상이면 반려)에 대해 다시 검토한 결과, 실제 저장된 사고
사례의 OCR 텍스트를 보면 **정상적인 단일 예약 건 하나(예: Hotels.com 같은 OTA로 예약)조차
호텔/OTA 자체 사업자번호 + 결제대행사(PG사) 사업자번호 + 카드사 관련 번호까지 겹쳐 2~3개가
나올 수 있다** — 즉 사업자번호 개수만으로는 정상적인 단일 예약도 오반려할 위험이 있다.

- **보완된 기준(2단계 신호)**: 사업자등록번호 3개 이상 **그리고** 서로 다른 체크인/투숙 날짜
  패턴이 2개 이상 함께 검출될 때만 "여러 건이 섞인 것 같습니다, 각각 따로 등록해 주세요"로
  반려한다. 실제 사고 사례는 두 신호 모두 강하게 나타났다(사업자번호 5개 + 서로 다른
  체크인 날짜 여러 개). 정상적인 단일 OTA 예약은 사업자번호는 여러 개 나와도 체크인 날짜는
  보통 하나뿐이라 두 번째 신호에서 걸리지 않아 통과한다.
  - 구현: 사업자등록번호 정규식(`\d{3}-\d{2}-\d{5}`)은 기존과 동일. 날짜 신호는 "체크인"
    주변 날짜, "거래일자/거래일시" 날짜 등 영수증에서 흔히 쓰이는 날짜 패턴을 추출해 서로
    다른 날짜(일 단위)가 몇 종류인지 센다.
  - `rules/domestic_travel_rules.json`의 숙박 섹션에 `max_business_numbers: 2`와
    `max_distinct_dates: 1`(또는 유사한 이름) 두 임계값을 신설, 조식의 `max_receipts`와는
    분리 관리한다.
- 참고: "영수증을 여러 장 따로 등록하는 것"과 "한 번의 업로드에 서로 다른 문서가 섞이는 것"은
  다른 문제다. 전자는 항목 8(출장 단위 누적 상한)로 막고, 후자만 이 항목으로 막는다.

### 8. 숙박 상한을 출장 단위 누적으로 — **채택, 예시 재설명**
사용자가 이해 안 된다고 한 원래 리포트의 예시(3건×35만원)가 혼란을 줬다 — 다시 설명하면:
- **지금 이미 잘 되는 경우**: 2박 출장(1박 상한 12만원 → 출장 전체 상한 24만원)에서 영수증이
  **1장만** 있고 26만원이면 → 24만원만 인정(PARTIAL). 사용자가 말한 예시와 정확히 일치하는
  동작이고, 이미 코드가 이렇게 하고 있다. **문제 없음.**
- **실제 버그**: 영수증이 **여러 장**일 때다. 같은 24만원 상한을, 영수증마다 매번 "출장 전체
  상한"과만 비교하고 다른 영수증에서 이미 얼마를 인정받았는지는 전혀 안 본다. 예를 들어 같은
  2박 출장에서 숙박 영수증을 20만원 + 20만원, 이렇게 2장으로 나눠 올리면 → 1번째: 20만원 ≤
  24만원이라 그대로 승인, 2번째도 20만원 ≤ 24만원이라 그대로 승인 → **합계 40만원 인정**
  (원래 상한 24만원을 16만원 초과).
- 조치: 숙박 영수증을 판정할 때마다, 같은 출장의 다른 숙박 영수증들이 이미 인정받은 금액의
  합계를 먼저 구하고, "남은 한도 = 출장 전체 상한 − 이미 인정된 합계"를 계산해서 이번 영수증은
  남은 한도까지만 인정한다(남은 한도가 0이면 반려: "이미 숙박비 상한에 도달했습니다"). 영수증을
  재분석하거나 삭제/재등록해도 항상 그 시점의 합계로 다시 계산되므로 순서에 상관없이 일관된다.

### 9. 비인증 API의 개인정보 노출 — **채택, 쉬운 설명 포함**
> 로그인 없이 주소(URL)만 알면 누구나 열어볼 수 있는 페이지가 있는데, 그중 `/api/trips`는 앱
> 화면 어디에서도 실제로 쓰이지 않는데 그냥 살아있어서, 그 주소를 직접 입력하면 전체 사용자의
> 출장 목록과 실제 이메일 주소가 그대로 보인다. 누가 일부러 그 주소를 찾아 들어갈 가능성은
> 낮지만, 남는 구멍은 막아두는 게 맞다.
- 조치: (a) 앱에서 안 쓰는 `GET /api/trips` 라우트 삭제. (b) 실제로 쓰는 다른 라우트
  (`GET /api/receipts?tripId=`, `GET /api/trips/[id]/pdf`, `DELETE /api/receipts?id=`)에는
  요청자의 `owner_email` 쿠키와 그 출장의 소유자 이메일이 일치하는지 확인하는 절차를 추가해서,
  주소를 안다고 남의 자료를 보거나 지울 수 없게 막는다.

### 10. PDF 재분석 시 페이지 유실 — **채택**
렌더링한 모든 PDF 페이지를 Blob에 저장(현재는 1페이지만 저장)하거나, 최소한 PDF 출처 영수증을
재분석할 때 "일부 정보가 사라질 수 있습니다" 경고를 띄운다.

### 11. HEIC 처리 — **채택, 제안 변경(차단이 아니라 변환)**
> **Q: heic 파일로 볼 수 있게 한다는 의미면 찬성** → 맞다, 원래 리포트의 "허용 목록에서 HEIC를
> 빼서 브라우저가 알아서 바꾸게 하자"는 제안은 **막는 쪽**에 가까웠다. 대신 서버가 HEIC를
> 받아서 JPEG로 자동 변환하는 단계를 추가하는 쪽으로 제안을 바꾼다.
- 조치: `POST /api/receipts`에서 PDF를 이미지로 바꾸는 것과 같은 방식으로, 업로드된 파일이
  HEIC/HEIF면 서버에서 JPEG로 변환(`heic-convert` 같은 라이브러리 사용)한 뒤, 그 JPEG를
  OCR·PDF·화면표시 전부에 동일하게 사용한다. 이러면 아이폰이 미리 변환해주든 안 해주든 결과가
  같아져서, 기존 리포트의 "확인 불가" 항목(iOS 자동 변환 여부)도 더 이상 중요하지 않게 된다.

### 12. 빈 파일타입 → 오해 소지 있는 오류 메시지 — **재제안**
- 조치: (a) 업로드 전 `File.type`이 비어 있으면 파일 확장자(.jpg/.png/.heic 등)로 타입을
  추정해서 채워 넣는다. (b) 업로드 실패 원인을 구분해서 보여준다 — 형식/크기 문제면
  "지원하지 않는 파일 형식이거나 크기가 너무 큽니다", 진짜 통신 문제일 때만 "네트워크 오류"를
  띄운다.

### 13. 업로드 토큰 발급 검증 없음 — **재제안**
- 조치: `onBeforeGenerateToken`에서 (a) 경로의 `tripId`가 실제 존재하는 출장인지, (b) 요청의
  `owner_email` 쿠키가 그 출장의 소유자와 일치하는지 확인한 뒤에만 업로드 토큰을 발급한다.
  둘 중 하나라도 안 맞으면 토큰 발급 거부 — 무료 Blob 용량/트래픽이 외부에서 소진되는 것을 막는다.

### 14. OCR 폴백 금액 추정 — **채택**
"합계/총액" 키워드를 못 찾아 전체 텍스트에서 가장 큰 숫자를 금액으로 추측한 경우, 그 값을
자동판정에 바로 쓰지 않고 "추정값 — 확인 필요" 상태로 표시해 사용자가 검토하게 한다.

### 15. 잘못된 날짜 입력(13월, 45일) — **재제안**
- 조치: 날짜 입력 컴포넌트(`DateYMDInput.tsx`)와 API(`trips/route.ts`) 양쪽에서 월 1~12, 일은
  해당 월의 실제 일수 범위인지 확인한다. 벗어나면 500 에러 대신 "날짜를 확인해 주세요" 같은
  안내와 함께 400으로 막는다.

### 16. `POST /api/trips` 본문 파싱 오류 미처리 — **재제안**

  "요청 형식이 올바르지 않습니다" 400을 반환한다.
